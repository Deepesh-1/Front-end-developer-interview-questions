"Walk me through ThreadCraft."

ThreadCraft is an e-commerce platform for premium T-shirts, built with Next.js 15's App Router, TypeScript in strict mode, GraphQL as the API layer, and PostgreSQL via Prisma for persistence. I was the sole engineer — responsible for every architectural decision, from routing structure to the auth flow to state management, not just implementation.

Architecture, high level: the frontend is a Next.js app that defaults to Server Components for anything that just displays data, and drops into Client Components only where real interactivity is needed — search inputs, the cart, forms. It talks to a GraphQL API — resolvers backed by Prisma — running inside the same Next.js deployment as route handlers, so there's no separate backend service to manage. Auth is JWT-based, with tokens in httpOnly cookies rather than localStorage, specifically to close off XSS token theft.

[If asked to draw it: container diagram — Browser, with React components and a Redux cart store, talking over HTTPS to the Next.js server, which hosts route handlers, GraphQL resolvers, and the auth layer, which in turn talks to Postgres through Prisma.]

Project flow: a customer lands on the home page, which shows three fixed categories — Developer, Gym, Travel. They can either browse a specific category or hit the full product listing, both of which support search, filtering, sorting, and paginate via a "Load more" pattern rather than infinite scroll — I chose that deliberately for accessibility and to avoid the classic infinite-scroll problems with the back button and unreachable footers. From a product card, they go to the detail page — gallery, size/color selection, stock status — add to cart, and go through a multi-step checkout: customer info, shipping, order summary, mocked payment, confirmation.

Folder structure follows two axes at once: component-based and feature-based. components/ui holds generic, domain-agnostic primitives — Button, Input, Modal — that don't know what a product is. features/products, features/cart, features/auth each hold their own components, hooks, and GraphQL queries scoped to that domain. app/ stays thin — just routing — delegating real logic into features. I only create a feature folder once a real feature needs it, not speculatively.

Rendering strategy per page — this is deliberate, not default. The homepage is fully static, since the three categories never change. Product listing and detail pages are server-rendered per request, since inventory and pricing can change. I'd actually reach for ISR on the listing pages in production — mostly static for speed, but regenerating in the background every so often so it doesn't go stale — versus full SSR on something like the account/orders page, which is genuinely per-user and shouldn't be cached at all.

API communication: GraphQL, not REST. The frontend uses Apollo Client, which gives normalized caching — if a product shows up in both the listing and a "recently viewed" widget, Apollo dedupes it into one cache entry instead of two separate copies. Queries are typed end-to-end using GraphQL Code Generator, so a schema change surfaces as a TypeScript error at build time, not a runtime bug. I chose GraphQL over REST specifically because the product detail page needs deeply nested data — images, variants, reviews, related products — in one round trip; doing that over REST would mean either over-fetching with a bloated endpoint or chaining several requests.

Caching: two layers. Apollo's normalized client-side cache handles repeated data across components without redundant network calls. On the Next.js side, I use the built-in data cache with ISR for pages like the product listing, and explicit revalidation tags so that when an admin updates a product, I can invalidate just that entry instead of the whole cache.

State management is matched per state type, not one global store for everything: cart lives in Redux Toolkit, because it's non-trivial derived state — totals, stock validation — that needs to persist across navigation. Search, filter, sort, and pagination live in the URL, not React state, so listings are shareable and survive a refresh. Auth session is a thin Context wrapping a server-verified cookie. Server-owned data — products, orders — stays in Apollo's cache and is never duplicated into Redux.

Why CSS Modules over Tailwind: I evaluated Tailwind early on and made a deliberate call to use CSS Modules with a centralized design-token layer instead — three tiers, primitive tokens, semantic tokens, component tokens — giving the same consistency benefits without a utility-class-heavy syntax, and it kept styling decisions colocated with each component rather than scattered inline in JSX.

Performance: next/image for automatic resizing, lazy loading, and layout-shift prevention across product photography — genuinely the highest-leverage win for an image-heavy catalog. Code-splitting is automatic per route, plus manual next/dynamic splits for anything heavy, like a chart on the admin dashboard. I only reach for useMemo/useCallback/React.memo where a profiler actually shows a re-render cost — not reflexively.

Security: JWTs signed and verified server-side only, stored in httpOnly, secure, sameSite cookies. Passwords hashed with bcrypt, never stored or compared in plain text. RBAC enforced server-side, in the GraphQL resolvers themselves — never trusting a frontend role check alone, since that's trivially bypassable. A Content Security Policy restricting script sources, input sanitization on anything user-generated, and CSRF mitigation via sameSite cookies plus explicit tokens on state-changing mutations.
